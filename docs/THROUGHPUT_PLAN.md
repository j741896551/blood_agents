# 多智能体服务吞吐与并发验证计划

本计划只规定测试方法和扩容顺序，**不是已经达到的并发指标**。现有证据仅包括本地同/跨会话并发回归和主模型直连 1/2/4 路小样本；尚未用 30/50 个虚拟用户压测完整 `/chat` 链路。真实平台 API 由用户自行配置和试用，自动化测试不能未经确认直接耗费模型额度。

## 1. 先区分“用户数”和“模型并发”

一次对话可能依次调用导航、领域理解/工具规划、FAQ 证据核验、回复与后台画像模型，且会访问 Mock HTTP/MCP、SQLite 和 LangGraph checkpoint。50 个在线虚拟用户不等于恰好 50 个同时在途模型请求；应同时记录活跃会话数、入口在途请求数、每阶段模型在途数、每秒完成轮次和端到端时延。当前主/备 `LLM_MAX_CONCURRENCY` 默认各为 1；在该配置下不能承诺几十个用户同时得到及时回复。一次模型网关默认总等待预算 60 秒，不是整轮对话的 SLA。

当前约束：FastAPI `/chat` 是同步处理；同一 user_id/session_id 的锁仅在单进程内生效；默认本地 SQLite/SqliteSaver 及 Mock 业务库会争用文件锁；MCP stdio 查询目前每次 `tools/call` 都建立子进程/客户端；模型请求超时后底层任务可能继续占用提供方在途名额。直接增加 Uvicorn Worker 数量会绕过进程内会话锁和模型总在途控制，不能当作安全扩容。

## 2. 可复现的虚拟用户负载

**环境隔离**：只使用独立临时 Mock/Checkpoint 数据库、合成 user_id 和 session_id；每个虚拟用户保持自己的会话，多轮顺序发送；不要对真实公司接口或日常演示库做写入压测。固定随机种子、语料版本、代码版本、Python/硬件、向量后端、模型配置、超时和在途上限。

**场景混合（首版假设，后续用真实匿名化流量分布校正）**：FAQ/知识追问 35%，预约查询与预约收集/确认 25%，积分/礼品/订单只读 20%，献血记录及“下次献血”跨 RAG+记录 15%，新建/取消等合成写操作 5%。每个场景至少 2–4 轮，轮间随机思考 2–15 秒；长尾还应包含无证据问法、失败回执、缓存唯一命中、MCP 路径、同会话快速连发及用户中途放弃。写操作使用不同身份/时段及幂等键，单独统计，不用库存冲突污染服务可用性指标。

**阶梯**：先 1/5/10 人校准，再 30 人、50 人各保持 10–15 分钟，记录预热与稳定期；到达门槛后才做 100/200 人和突增/恢复测试。分别运行 `local`、`http`、`mcp` transport；分别运行“固定延迟/故障注入的假模型”与获用户许可的真实平台模型。前者测本应用编排/数据层容量，后者才测平台配额、网络、成本与真实回复质量，两者报告不得混算。

**入口**：对独立启动的 FastAPI `/chat` 发 HTTP 请求，而非只调用内存图或 `TestClient`。驱动器用异步 HTTP 客户端并发模拟完整会话、思考时间和实际到达节奏；测试机与被测服务尽量分开。Gradio 可做少量浏览器体验/按钮回归，但不是高并发吞吐的主要入口。`provider_probe.py` 只用于少量供应商直连探测，不代表应用压测。

## 3. 指标、正确性与停止条件

- 逐轮：成功/明确容量拒绝/429/5xx/超时比例、p50/p95/p99 端到端时延、TTFT（仅流式导航）、完成轮次/秒、各阶段耗时与模型调用次数、token 与估算费用。
- 资源：进程 CPU/RSS、线程数、事件循环/线程池排队、SQLite 锁等待与 WAL/checkpoint 耗时、HTTP 连接数、MCP 子进程数、主备模型实际在途/排队/熔断/切换次数。
- 正确性：不同用户/会话无串话，预约/兑换只在确认后写入且无重复提交，同会话顺序保持，查询失败不编造事实，降级有明确错误回执；每轮可用 trace_id 串起节点与工具。
- 停止条件：出现跨用户数据、越权/重复写入、数据库损坏，或错误/超时连续上升并持续超出预设阈值，立即停止升阶；压力驱动器也要限制每秒请求和最大并发，避免无预算地消耗平台 API。

首轮报告先给出容量曲线和瓶颈，不先填“支持 50 并发”的结论。验收阈值在执行前结合模型平台限额与演示体验约定；最低必须做到 30/50 虚拟用户各完成稳定期测试，报告样本数、失败类别、p95/p99、吞吐和跨会话/写入正确性。任一真实模型 429/限流或本地 `busy` 都是容量边界，不按成功处理。

## 4. 如何从几十人扩到更高并发

1. **先测后调**：按阶段 trace 找最长链路；减少不必要的模型调用、控制检索/重排开销，对已审核且唯一匹配的标准问答使用现有缓存；不能缓存个人、实时或混合问题。
2. **有界排队与背压**：在入口和各模型供应商设置统一的并发/队列预算、超时和明确的 429/503；根据平台实际 RPM/TPM、延迟和成本逐步提高主备在途上限。不要把无限线程或无限排队当抗压能力。主备同时故障时保留“服务不可用”，不能凭模板回复业务结论。
3. **消除局部热点**：对 MCP 高频只读查询评估复用长生命周期连接/进程或网络传输；HTTP 客户端连接池和 SQLite WAL/锁等待要单独量化。该优化必须保留 user_id 隔离和工具回执契约。
4. **再水平扩容**：若单进程极限仍不足，先把 checkpoint/对话/Mock 业务数据迁移到适合并发的共享存储，并实现跨进程同会话锁或乐观版本控制、分布式限流与幂等；之后才增加 API Worker/实例和负载均衡。仅给现有 SQLite 程序加 Worker 不是安全方案。
5. **持续验证**：每次提高上限或换存储后重跑 30/50/100+ 人混合场景、故障/恢复及成本测试；最终作品集只展示在指定环境里测到的容量，不推断真实血站生产容量。
