# 多轮对话 Excel 自动化评测

这套测试直接调用项目的 LangGraph 入口，不依赖手动打开 Gradio。每个场景使用独立临时 SQLite + Mock 业务接口；场景内各轮共用 `user_id` 和会话 checkpoint，所以能检验多轮状态。**不会写入网页演示数据库，也不会接入公司的真实旧接口。**

## 运行

```bash
# 固定话术批量验证：被测智能体和整场评审都必须调用模型，可能产生费用。
BLOOD_AGENT_TRACE_MODE=off .venv312/bin/python -m blood_agents.evals.conversation_evaluation \
  --dataset evals/conversations/batch_review_example.xlsx
```

上面 `--dataset` 指定的就是输入 Excel；示例命令使用 `evals/conversations/batch_review_example.xlsx`，含 5 个独立场景、18 轮固定话术。评测器没有内置默认输入，运行时必须填写 `--dataset`。可改为自己的 `.xlsx` 文件路径；另有 `evals/conversations/appointment_lifecycle.xlsx` 作为较小的预约生命周期示例。输出默认位于 `evals/reports/`，每次以运行 ID 生成一对 `<运行ID>.xlsx` 和 `<运行ID>.json`，不覆盖旧报告。输出 Excel 含“总览”“对话结果”“对话评审”“执行证据”四页；`--output-dir` 可改变输出目录。JSON 用于机器追溯，主要阅读 Excel。

FAQ 与主导航最终答复另有 `evals/conversations/faq_final_reply.xlsx`：4 个场景、6 轮固定话术。其中 3 个 FAQ 场景、4 轮覆盖公开法条连续追问、公开科普和个人医学资格无证据问题；1 个主导航场景、2 轮检查演示系统的数据来源和无回执边界。把命令中的 `--dataset` 改为该文件即可运行；每轮会调用模型，另按场景调用模型评审。评审输入现在包含 FAQ 本轮实际交给回复模型的**已核验知识片段与来源**，因此可检查最终答复有没有超出片段。主导航场景不应误走 `knowledge_search`，而应依据服务端提供的演示系统事实作答。检索/核验状态和模型评审是不同证据：来源引用与评审通过都不能替代人工医学复核。2026-10-20 的首次真实模型评测针对修订前的用例；修订后的用例已另行复测，两份报告须按用例 SHA-256 区分，结果见 `PROJECT.md`。
2026-10-20 已对修订后的同一 Excel 重新运行真实模型，报告和人工复核结果见 `PROJECT.md`。单次通过不能替代更多问法或个人医学问题的证据审查。

运行时终端会实时打印中文进度：输入与报告目录、场景开始、逐轮开始/结束、意图与模型模式、整场模型评审状态、报告保存路径和最终判定。单次模型调用等待超过 10 秒时会继续打印等待时长。这些进度日志不受 `BLOOD_AGENT_TRACE_MODE=off` 影响；该变量只关闭详细的图与模型追踪。如需查看模型请求/响应、节点和工具细节，改用 `BLOOD_AGENT_TRACE_MODE=full`，并按下方隐私提示保管日志。

正式入口没有关闭模型理解、回复或评审的开关。被测智能体使用当前 `.env` 的主备模型配置；所有轮次完成后，评审模型逐场景审核，目前复用同一套主备配置，尚非独立供应商。大量场景会产生多次模型调用与费用，建议先用少量用例验证配置和输出。未配置模型、调用失败、规则降级或评审输出不符合契约均不得通过。固定话术不会根据智能体回复动态生成下一句。内部单元测试仍可注入可控模型或运行离线编排诊断，但它们不属于模型对话验收。

默认报告写到被 Git 忽略的 `evals/reports/`，每次生成同名 `.xlsx` 和 `.json`，文件权限为 `0600`，不覆盖历史运行。Excel 的 `总览` 分开展示逐轮模型调用/结构检查、对话评审及用例内容 SHA-256 指纹；对比两次成绩时先核对指纹是否相同。`对话结果` 展示每轮话术、回复和判定；`对话评审` 展示场景目标、模型结论、问题轮次及原文证据；`执行证据` 展示节点、工具和回执摘要。JSON 保留完整结构供程序追溯。退出码 `0` 仅在逐轮模型路径、显式断言和全部场景模型评审同时通过时返回。运行时控制台可能输出项目追踪日志；想查看完整模型输入/输出，可以另设 `BLOOD_AGENT_TRACE_MODE=full`、`BLOOD_AGENT_TRACE_FILE=./logs/...`，但日志含用户话术和模型内容，务必只使用合成身份并妥善保管。

## 如何提交自己的对话

复制 [`batch_review_example.xlsx`](../evals/conversations/batch_review_example.xlsx)，在 Excel/WPS/Numbers 中编辑三张输入表。一个“场景ID”对应一次独立对话；同场景的对话行按表格顺序构成多轮，不同场景各有独立临时 Mock 数据库和会话：

1. `场景`：一行一个独立场景，填写场景 ID、说明、合成用户 ID、预置数据和“对话评审目标”。示例提供新建、查询、取消、预约→查询→取消、签到等 5 个对话。评审目标要写可观察的互动目的，例如“确认后才宣称预约成功”，不要写“模型回复好一点”。需要 U1002 四状态旧记录时在“预置四状态预约”填“是”；默认 U1001 没有已提交预约。旧四列表格仍可导入，但建议补上第五列目标。
2. `对话`：一行一轮，按行顺序填写“场景ID、轮次ID、用户话术”；同一场景的多轮共用会话与 Mock 数据。
   当上轮 Mock 回执生成随机编号时，后续固定话术可写 `{{address_id:轮次ID}}` 或 `{{redemption_id:轮次ID}}`。运行器只从**同一场景此前轮次的结构化回执**取编号并替换；若前轮没有该编号，该场景报错，不会让模型猜测。报告保存替换后的实际话术。
3. `断言`：对要自动检查的轮次逐行填写“场景ID、轮次ID、检查项、预期值”。一个轮次可有多行。可用“必须经过节点、禁止经过节点、节点顺序”检查实际 LangGraph 路径。`填写说明` 工作表列出简短指引。没有断言的轮次只检查模型路径并标为**模型路径通过，业务未断言**；能否达到对话目标仍由整场模型评审判断，不能解释为业务正确。

保存成自己的 `.xlsx`，运行时将 `--dataset` 改为该文件路径即可。注意不要删除或修改三张输入表的首行列名；输入表不接受公式、宏、外链；仅把话术作为文本。只用合成身份数据，避免将真实姓名、证件、手机号、密钥写入测试集或报告。

现有 JSON 用例仍可作为兼容输入；但推荐直接改 Excel，不必手写 JSON。JSON 结构示例如下：

```json
{
  "version": 1,
  "name": "我的预约测试",
  "cases": [{
    "id": "cancel_after_query",
    "description": "取消必须有查询依据和二次确认",
    "user_id": "U1001",
    "turns": [
      {"id": "ask", "message": "查询我的预约记录", "expected": {
        "intent": "appointment", "tools_exact": ["query_user_appointments"]
      }},
      {"id": "observe", "message": "你好"}
    ]
  }]
}
```

每个 `case` 独立初始化；`seed_appointment_samples: true` 可加入 U1002 四状态合成历史。可参照示例用例编写新建→查询→取消、签到等完整流程。

Excel 的“检查项”只检查写出的字段，可使用：

- 意图和流程：`意图`、`动作`、`智能体状态`、`活动智能体`、`槽位.日期/网点/时段`；
- 业务结果：`结果状态`、`结果码`、`操作成功`、`操作`、`数据状态`、`预约状态`；
- 工具边界：`工具顺序`、`必须调用工具`、`禁止调用工具`。工具顺序等多值检查按多行填写，顺序保持一致；
- 图路径：`节点顺序`、`必须经过节点`、`禁止经过节点`。前者比较完整路径，后两者分别做包含/排除检查；
- 跨轮一致性：`预约号同前轮` 的值写当前场景前面某个轮次 ID；
- 回复：`回复模式`、`回复包含`、`回复不包含`。谨慎使用固定措辞断言，模型可能有语义等价表达。
- 预约确认门禁：`可确认预览` 填 `是/否`，检查服务端是否保留下一轮确认资格。预约、取消、签到的正向预览轮次建议同时断言 `回复模式=llm` 与 `可确认预览=是`；这两项仅证明回复节点接受模型预览并设置了服务端状态，不能证明浏览器已实际展示内容。

`appointment_lifecycle.xlsx` 的三个正向预览轮次已采用上述断言。离线诊断中无模型时，预览可得到 `preview_unavailable` 且再次确认不调用写工具；即使这类**负向诊断断言**全部符合预期，也仅表示安全边界按预期工作，不是模型对话验收通过。正式批测仍要求被测模型和整场模型评审，不要把离线结果填成预约成功率。

报告每轮保存脱敏的用户话术与答复、判定原因、`trace_id`、模型理解/回复模式、节点路径、工具轨迹和结构化结果。每轮均检查导航理解和回复是否由 LLM 完成；预约轮另检查预约理解，以及需规划时的工具规划是否走模型。即使没有显式断言，模型不可用或规则降级也会标失败。模型评审不能覆盖这些程序门禁。

模型评审只评价整场对话是否完成“对话评审目标”、追问是否合适、回复是否切题以及“已完成”宣称是否有工具回执依据；不裁判 Mock 库存或旧业务规则是否正确。模型必须输出结构化结论；每个问题要指出轮次，并逐字引用该轮用户话术或回复，引用无效则标“不可评审”。节点/工具检查由程序完成，模型评审不能覆盖程序失败。评审本身仍可能误判，应人工复核失败与抽样通过场景；同一模型兼任被测模型和评审模型也存在偏差。

自动判定以结构化事实为主；未写出的语义和“对话是否自然”没有被自动证明。建议先固定关键业务断言，再对失败/待评的 Excel“对话结果”做人工复核，最后把发现的问题沉淀成新用例。真实模型运行有随机性，应记录日期、模型/供应商、样本量和重复次数；单次通过不是准确率或生产可用性证明。
